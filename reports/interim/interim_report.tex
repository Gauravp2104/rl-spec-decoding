\section{Introduction and Scope}

Speculative decoding lets a small \emph{draft} model propose $K$ tokens that a large \emph{target} model verifies
in one forward pass; verification keeps the longest correct prefix plus one target token, so the output is
exactly the target's. The speed-up depends almost entirely on the mean acceptance length $\taubar$ (accepted
draft tokens per verification step). Our proposal argued, following Aurora~\cite{aurora}, that drafter training
should be \emph{online}, and proposed replacing Aurora's forward-KL distillation loss with an off-policy GRPO
objective that rewards accepted length directly.

\paragraph{Change of plan since the proposal.} The full Aurora stack needs about six 80\,GB GPUs for Qwen3-8B
(SGLang at TP=4 plus two FSDP training GPUs) and is CUDA-only (SGLang, Mooncake, Ray, FSDP2, FlexAttention).
We first need a working forward-KL baseline that we fully control, so the project has two phases:
\begin{enumerate}
  \item \textbf{Base-paper reproduction (nearly complete):} Aurora's online EAGLE-3 training, scaled down to
  Qwen3-0.6B on Apple-silicon laptops (PyTorch MPS backend). We reuse Aurora's model, loss and data code
  and replace only the serving and orchestration infrastructure, in nine sub-tasks (BP-01 to BP-09).
  \item \textbf{GRPO extension (next):} the off-policy GRPO objective from the proposal, built on the
  reproduction. The reproduction already logs the quantities GRPO needs: per-round accepted length (the
  reward) and, for every round, the served draft version and the trainer's version (the staleness $\Delta$).
\end{enumerate}

\paragraph{Data (BP-02).} Aurora's mixed-domain training data is private, so we built public replacements:
1000 conversations each from ShareGPT (chat), CodeAlpaca-20k (code) and GSM8K (math), filtered to start with
a user turn and to fit in 1024 tokens. From these pools we emit three request streams: \emph{mixed} (3000
requests, shuffled), \emph{ordered} (3000, grouped by domain) and \emph{domain-shift} (1200: 600 chat, then
300 code, then 300 math). The draft predicts a reduced 24K-token vocabulary (out of Qwen3's 152K), built from
assistant-token frequencies on the mixed stream with Aurora's \code{generate\_vocab\_mapping}.

\paragraph{Models (BP-03).} The target is Qwen3-0.6B (596M parameters), with auxiliary hidden states captured
from layers 1, 13 and 24. The EAGLE-3 draft is a single Llama decoder layer (hidden size 1024) fed by a linear
fusion of the three auxiliary states (3072$\to$1024) and the token embedding: 42.4M trainable parameters (24.6M
in its own 24K-row output head) plus a frozen 155.6M-parameter embedding copied from the target. Training uses
Aurora's \code{Eagle3Model} with a three-step test-time-training (TTT) unroll and loss $\sum_i 0.8^i\,\mathcal{L}_i$,
where $\mathcal{L}_i$ is the cross-entropy against the target's soft distribution at unroll step $i$.

\paragraph{Static baseline (BP-04).} No public EAGLE-3 draft exists for Qwen3-0.6B, so we trained one offline on
the chat pool, holding out its last 100 conversations: AdamW at $10^{-4}$, warmup plus cosine, effective batch
8, fp32 weights, gradient checkpointing, 8 epochs (896 steps, 19 minutes on MPS). The checkpoint is published as
a GitHub release (\code{bp04-static-v1}) so that every member starts from identical weights. It is both the
\emph{static} baseline and the initialisation for Aurora's \emph{with-draft} mode.

\paragraph{Inference server (BP-05).} This replaces SGLang with an HF-transformers loop at batch size 1. Each
round the draft proposes $K=3$ guesses and the target scores them in one pass using a \code{DynamicCache}
(cropped on rejection), with greedy (exact argmax match) or speculative-sampling ($\min(1,p/q)$, residual
resampling) acceptance. It logs per-round accepted lengths and draft versions, emits Aurora-format training
samples, and can load new draft weights between requests.

\paragraph{Online loop (BP-06).} The server's training samples go into a bounded \emph{sample pool} (128
samples, kept on the CPU). As in Aurora, serving blocks when the pool is full rather than dropping samples. A
separate \emph{online trainer} owns its own fp32 copy of the draft and runs the BP-04 recipe on batches from the
pool at a constant learning rate ($10^{-4}$ day-0, $10^{-5}$ with-draft). Every $N$ steps it \emph{publishes} a
copy of its weights into a single pending slot, versioned by its step count; the server applies it before its
next request. In \emph{sync} mode the loop alternates between serving $B$ requests and training $M$ steps. In
\emph{async} mode a serving thread and a training thread run concurrently; because the MPS backend aborts when
two threads issue GPU work at once, a FIFO device lock serialises their GPU calls. Every request records the
trainer's version, so per-round staleness $\Delta$ is exact.

\paragraph{Evaluation tooling (BP-07).} All metrics are recomputed from a run's request log and training log:
rolling $\taubar$, per-position acceptance $\alpha_i$, acceptance rate, tokens/s against target-only decoding,
the estimated speed-up $(1+\taubar)/(1+Kc)$, staleness and the loss curve. A latency bench measures $c$, the
cost of one draft step relative to one target step. Output is CSV, JSON and plots. The repository has 68 tests,
including losslessness under live weight swaps in sync and async modes.

\section{Baselines and State of the Art}
\label{sec:baselines}

\paragraph{Lineage.} Speculative decoding with lossless verification was introduced by Leviathan et
al.~\cite{leviathan} and Chen et al.~\cite{chen}. Medusa~\cite{medusa} added parallel decoding heads to the
target. The EAGLE family~\cite{eagle,eagle2,eagle3} drafts from the target's hidden states. EAGLE-3 fuses
low-, mid- and high-level features and trains with a test-time-training unroll; it is the drafter used by
Aurora and by us. Online Speculative Decoding~\cite{osd} first proposed distilling the draft on live traffic.
Aurora~\cite{aurora} makes this practical as a unified training--serving system with asynchronous weight
hot-swap, and is the state of the art we reproduce. GRPO~\cite{grpo} is the critic-free RL objective our
extension adapts.

\paragraph{Systems we compare.} All are evaluated on the same streams, hardware and decoding settings:
(1)~\textbf{target only}, the speed-up reference; (2)~\textbf{static EAGLE-3}, the frozen BP-04 draft, i.e.\ the
``train offline, then deploy'' pipeline Aurora argues against; (3)~\textbf{Aurora day-0}, online forward-KL
training from a random draft; (4)~\textbf{Aurora with-draft}, online forward-KL training from the static draft;
(5)~\textbf{ours}, off-policy GRPO with a forward-KL anchor, with the ablations from the proposal (synchronous
on-policy GRPO, $\Delta=0$; group size $G$; KL weight $\beta$; clipping and truncation thresholds; reward shaping).

\paragraph{Planned experiments (BP-08).} \textbf{E1}: day-0 online training against target-only on the mixed
stream (partly done: Section~\ref{sec:results}). \textbf{E2}: static draft vs.\ with-draft online training under the
chat$\to$code$\to$math shift; Aurora's main claim is faster recovery after a shift, which we measure as the area
under the rolling-$\taubar$ curve after each shift. \textbf{E3}: E2 on the ordered stream. \textbf{E4}:
sensitivity to the sync interval $N\in\{5,20,50\}$, the learning rate, and sync vs.\ async training. The
headline metric is $\taubar$, which does not depend on hardware; we also report $\alpha_i$, measured and
estimated speed-up, and the staleness distribution.

\section{Evaluation Results (Prototype)}
\label{sec:results}

All runs use greedy decoding, $K=3$, fp32 target and draft, and up to 128 new tokens. BP-03 to BP-05 ran on an
M5 Pro (24\,GB); the BP-06 run ran on a MacBook Air (16\,GB). Tokens/s is therefore only compared within a run.

\paragraph{Correctness.} Speculative output is token-identical to target-only decoding on every request checked:
50/50 stream prompts and 100/100 held-out chat requests with a fixed draft (BP-05), and \textbf{300/300} requests
of the online run while the draft's weights were replaced 30 times (BP-06).

\paragraph{Draft trainability and static baseline (BP-03, BP-04).} On one fixed batch the draft overfits in 200
steps (loss 9.87$\to$0.851 against a target-entropy floor of 0.849; accuracy 0.99 / 0.99 / 0.98). The static
draft's held-out accuracy (draft argmax equals target argmax, teacher-forced) rises from 0.183 after epoch 1 to
0.245 after epoch 2 and \textbf{0.310 / 0.270 / 0.248} after epoch 8, plateauing after epoch 6. A 2-epoch run
gives the same numbers on a Kaggle T4 and on MPS, and the released T4 8-epoch checkpoint matches the MPS one
($\taubar$ 0.315 vs.\ 0.313).

\paragraph{Static draft in the server (BP-05).} Table~\ref{tab:serve} gives end-to-end results on the M5 Pro.
The upper rows are sanity bounds: an untrained draft accepts nothing, while a draft overfitted to the exact
answers reaches $\taubar=2.6$ and twice the target-only speed, so the server can deliver a real speed-up when
the draft guesses well. On held-out chat the trained static draft reaches $\taubar=0.313$.

A with-draft smoke run (20 mixed requests, starting from the released static draft, learning rate $10^{-5}$)
starts at $\taubar\approx0.26$ immediately, which the day-0 draft only reaches after about 300 requests. A
full with-draft run is part of E2.

\paragraph{What the numbers say.}
\begin{enumerate}
  \item \textbf{Online learning works from scratch.} With only 150 steps on about 34K completion tokens, the
  day-0 draft reaches 80\% of the static draft's $\taubar$, which needed 896 offline steps. It learns fastest on
  math, whose text is the most predictable (math $0.115\to0.318$, code $0.074\to0.226$, chat $0.050\to0.126$,
  first vs.\ last third of each domain's requests).
  \item \textbf{Acceptance is almost all at the first guess.} $\alpha_2$ and $\alpha_3$ stay small for both
  drafts. Guesses 2--3 are built on the draft's own hidden states, and a chain stops at the first miss, so
  errors compound. Teacher-forced accuracy (0.31 / 0.27 / 0.25) therefore overstates live acceptance. Positions
  2--3 are exactly where an acceptance-based reward differs most from forward KL, which weights all positions
  equally.
  \item \textbf{Staleness is small and harmless.} The served draft lags the trainer by 0--4 steps (mean 1.96),
  and losslessness held through every swap.
  \item \textbf{Still slower than the target alone.} A round costs about 2.2--2.3 target-only steps (68\,ms on
  the Air, 41\,ms on the M5 Pro) but yields only $1+\taubar$ tokens, so break-even needs $\taubar\approx1.2$--$1.3$.
  The estimate (0.89$\times$) is more optimistic than the measurement (0.53$\times$) because it leaves out the
  $(K{+}1)$-token verify pass, the draft re-reading a growing context (it has no KV cache yet) and per-round
  overhead.
\end{enumerate}

\paragraph{Relation to published results.} Papers usually report acceptance length as tokens per target pass,
which is $1+\taubar$ in our notation. Published EAGLE-2/3 drafts with tree drafting on 8B--70B targets report
roughly 4--6+ tokens per pass and 3--6$\times$ speed-ups; chain-style methods such as classic speculative
decoding and Medusa report about 2--3$\times$~\cite{leviathan,medusa,eagle2,eagle3}. We are at 1.25--1.31
tokens per pass and below 1$\times$. The gap is expected: our drafts have seen thousands rather than hundreds of
thousands of training conversations, we draft one chain of $K=3$ instead of a tree, a 0.6B target makes the
draft's relative cost large ($c\approx0.1$), and MPS with batch size 1 lacks the kernels and batching of
production servers. We therefore compare systems \emph{against each other} on the same setup, with $\taubar$ as
the headline metric, rather than against published absolute speed-ups.

\section{Issues Faced}

\paragraph{Solved.}
\begin{itemize}
  \item \textbf{Compute and CUDA-only stack:} scaled down to Qwen3-0.6B on MPS, replacing SGLang, Mooncake, Ray
  and FSDP2 (Table~\ref{tab:mapping}) while reusing Aurora's algorithmic code unchanged.
  \item \textbf{No public draft, private data:} trained our own EAGLE-3 draft on public data; ShareGPT filters
  drop 939 threads that start mid-conversation and 613 longer than 1024 tokens.
  \item \textbf{Draft-vocab coverage:} 16K covered only 97.6\% of assistant tokens (others can never be drafted);
  24K covers 0.993 / 0.995 / 0.998 (chat / code / math) for 8.2M more parameters.
  \item \textbf{Memory:} 4$\times$1K-token batches needed 9.9\,GB (draft logits $\times$ 3 TTT steps); batch 2 with
  gradient checkpointing trains in 2.4\,GB, and the whole online loop peaks at 7.5\,GB, so it fits a 16\,GB laptop.
  \item \textbf{Precision:} pure-bf16 AdamW lost 2--3 accuracy points (small updates round away), so we train in
  fp32 like Aurora's master weights. In bf16, a 4-token verify pass rounds differently from 4 single steps and can
  flip near-ties, so losslessness checks run in fp32 (450/450 pass).
  \item \textbf{Threads on MPS:} MPS aborts when two threads use the GPU at once; async mode serialises GPU calls
  with a FIFO device lock.
  \item \textbf{Sharing checkpoints:} the 170\,MB static draft is a GitHub release with a SHA-256 checksum.
\end{itemize}

\paragraph{Open.}
\begin{itemize}
  \item \textbf{No wall-clock speed-up yet.} Levers: higher $\taubar$ (more online training, GRPO), a draft KV
  cache, and tree drafting.
  \item \textbf{Train/test overlap in the streams.} The 600 chat requests of the domain-shift stream, and 900 of
  the 1000 chat requests in the mixed stream, were BP-04 training prompts. This does not affect day-0 runs, but
  before E2/E3 we must rebuild the chat segments from held-out conversations or report on unseen requests only.
  \item \textbf{Single-device asynchrony.} With the device lock, ``async'' on one GPU interleaves rather than
  overlaps serving and training. Staleness is real but smaller than in Aurora's two-server layout; E4 will
  quantify the difference.
  \item \textbf{Hardware variance.} A fanless laptop slowed $\sim$12\% over an hour (the speed ratio held at
  0.53--0.54), so we only compare speeds within a run.
  \item \textbf{GRPO prerequisites.} Groups of rollouts need tree drafting (top-$k>1$), which is not yet
  implemented, and $K=3$ gives a shorter reward range than the paper's $K=5$.
\end{itemize}

  \item \textbf{GRPO extension:} tree drafting for groups; reward $R(a)=L(a)-\lambda\kappa(K-L(a))$ from the
  logged accepted lengths; the off-policy objective with truncated importance weights and the forward-KL
  anchor, using the logged staleness; and comparison against systems 2--4 above.
  \item \textbf{BP-09 (optional):} the same code on a CUDA GPU with a larger target, to check that the trends
  carry over.
\end{enumerate}
