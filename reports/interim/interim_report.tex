\section{Introduction and Scope}

Speculative decoding lets a small \emph{draft} model propose $K$ tokens that a large \emph{target} model verifies
in one forward pass; verification keeps the longest correct prefix plus one target token, so the output is
exactly the target's. The speed-up depends almost entirely on the mean acceptance length $\taubar$ (accepted
draft tokens per verification step). Our proposal argued, following Aurora~\cite{aurora}, that drafter training
should be \emph{online}, and proposed replacing Aurora's forward-KL distillation loss with an off-policy GRPO
objective that rewards accepted length directly.

\paragraph{Change of plan since the proposal.} The full Aurora stack needs about six 80\,GB GPUs for Qwen3-8B
(SGLang at TP=4 plus two FSDP training GPUs) and is CUDA-only (SGLang, Mooncake, Ray, FSDP2, FlexAttention).
Before changing the objective we need a working, measurable forward-KL baseline that we fully control. We
therefore split the project into two phases:
\begin{enumerate}
  \item \textbf{Base-paper reproduction (in progress):} Aurora's online EAGLE-3 training, scaled down to
  Qwen3-0.6B on a single Apple M5 Pro laptop (24\,GB unified memory, PyTorch MPS backend). We keep Aurora's
  algorithm and reuse its model, loss and data code, and replace only the serving and orchestration
  infrastructure. This phase is organised as nine sub-tasks (BP-01 to BP-09), each with its own issue,
  branch and pull request.
  \item \textbf{GRPO extension (next):} the off-policy GRPO objective from the proposal, built on the
  reproduction. The reproduction already logs the quantities GRPO needs: per-round accepted length (the
  reward) and the draft version that produced each guess (the staleness $\Delta$).
\end{enumerate}

\paragraph{Data (BP-02).} Aurora's mixed-domain training data is private, so we built public replacements:
1000 conversations each from ShareGPT (chat), CodeAlpaca-20k (code) and GSM8K (math), filtered to start with
a user turn and to fit in 1024 tokens. From these pools we emit three request streams: \emph{mixed} (3000
requests, shuffled), \emph{ordered} (3000, grouped by domain) and \emph{domain-shift} (1200: 600 chat, then
300 code, then 300 math). The draft predicts only a reduced 24K-token vocabulary (out of Qwen3's 152K), built
from assistant-token frequencies on the mixed stream with Aurora's \code{generate\_vocab\_mapping}.

\paragraph{Models (BP-03).} The target is Qwen3-0.6B (596M parameters), with auxiliary hidden states captured
from layers 1, 13 and 24 via forward hooks. The EAGLE-3 draft is a single Llama decoder layer (hidden size 1024)
fed by a linear fusion of the three auxiliary states (3072$\to$1024) and the token embedding. It has 42.4M
trainable parameters (24.6M of them in its own 24K-row output head) and a frozen 155.6M-parameter embedding
copied from the target. Training uses Aurora's \code{Eagle3Model} with a three-step test-time-training (TTT)
unroll and loss $\sum_i 0.8^i\,\mathcal{L}_i$, where $\mathcal{L}_i$ is the cross-entropy against the target's
soft distribution at unroll step $i$.

\paragraph{Static baseline (BP-04).} No public EAGLE-3 draft exists for Qwen3-0.6B, so we trained one offline.
We dump the target's hidden states once for the chat pool, holding out the last 100 conversations, and train on
the other 900: AdamW at learning rate $10^{-4}$, warmup plus cosine schedule, effective batch 8, fp32 weights,
gradient checkpointing, 8 epochs (896 steps, 19.4 minutes on MPS). This checkpoint is both the \emph{static}
baseline and the initialisation for Aurora's \emph{with-draft} mode.

\paragraph{Inference server (BP-05).} This replaces SGLang with an HF-transformers loop at batch size 1. Each
round the draft proposes $K=3$ guesses; the target scores all of them in one pass using a \code{DynamicCache}
(cropped on rejection). We implement both greedy acceptance (exact argmax match) and speculative-sampling
acceptance ($\min(1,p/q)$ with residual resampling). Every request is logged as one JSON line with per-round
accepted lengths and draft versions. The server also emits Aurora-format training samples (prompt plus
generated tokens, auxiliary hidden states, loss mask), and new draft weights can be loaded at any time with
the version tracked. A test suite of 42 tests covers the data, models, baseline and server, including
losslessness and a statistical test that speculative sampling matches the target's distribution.

\section{Baselines and State of the Art}
\label{sec:baselines}

\paragraph{Lineage.} Speculative decoding with lossless verification was introduced by Leviathan et
al.~\cite{leviathan} and Chen et al.~\cite{chen}. Medusa~\cite{medusa} added parallel decoding heads to the
target. The EAGLE family~\cite{eagle,eagle2,eagle3} drafts from the target's hidden states. EAGLE-3 fuses
low-, mid- and high-level features and trains with a test-time-training unroll; it is the drafter used by
Aurora and by us. Online Speculative Decoding~\cite{osd} first proposed distilling the draft on live traffic.
Aurora~\cite{aurora} makes this practical as a unified training--serving system with asynchronous weight
hot-swap, and is the state of the art we reproduce. GRPO~\cite{grpo} is the critic-free RL objective our
extension adapts.

\paragraph{Systems we compare.} All are evaluated on the same streams, hardware and decoding settings:
\begin{enumerate}
  \item \textbf{Target only:} plain autoregressive decoding, the speed-up reference.
  \item \textbf{Static EAGLE-3:} the BP-04 draft, frozen. This is the ``train offline, then deploy''
  pipeline Aurora argues against.
  \item \textbf{Aurora, day-0:} online forward-KL training from a random draft.
  \item \textbf{Aurora, with-draft:} online forward-KL training starting from the static draft.
  \item \textbf{Ours:} off-policy GRPO with a forward-KL anchor, plus the ablations from the proposal:
  synchronous on-policy GRPO ($\Delta=0$), group size $G$, KL weight $\beta$, clipping and truncation
  thresholds, and reward shaping.
\end{enumerate}

\paragraph{Planned experiments (BP-08).} \textbf{E1}: is day-0 online training better than target-only on the
mixed stream? \textbf{E2}: static draft vs.\ with-draft online training under the chat$\to$code$\to$math
shift (Aurora's main claim is faster recovery after a shift). \textbf{E3}: E2 on the ordered stream.
\textbf{E4}: sensitivity to the sync interval $N\in\{5,20,50\}$, the learning rate, and sync vs.\ async
training. The headline metric is $\taubar$, which does not depend on hardware. We also report per-position
acceptance $\alpha_i$, measured tokens/s, the estimated speed-up $(1+\taubar)/(1+Kc)$ (where $c$ is the
measured draft-to-target cost ratio), the staleness distribution and the area under the rolling-$\taubar$
curve after each shift.

\section{Evaluation Results (Prototype)}

All numbers below are from the M5 Pro (MPS) with greedy decoding, $K=3$, fp32, and up to 128 new tokens.

\paragraph{Correctness.} Speculative output is token-identical to target-only \code{generate} on 50/50
stream prompts (18 chat, 17 code, 15 math) and on 100/100 held-out chat requests. This holds both with the
KV cache and in the cache-free reference path.

\paragraph{Draft trainability (BP-03).} On one fixed batch (4 sequences of 95 tokens) the draft overfits in
200 steps: loss falls from 9.87 to 0.851 against a target-entropy floor of 0.849, the remaining KL is 0.002,
and accuracy is 0.99 / 0.99 / 0.98 at the three TTT positions. An AdamW step takes 98\,ms and peak memory is
3.3\,GB. On real 4$\times$1025-token batches with the 24K vocab, peak memory is 9.9\,GB in fp32, and 7.2\,GB
with bf16 and gradient checkpointing.

\paragraph{Static baseline (BP-04).} Table~\ref{tab:bp04} shows held-out accuracy (draft argmax equals target
argmax, teacher-forced) during the 8-epoch run. The 2-epoch run gives the same numbers on a Kaggle T4 and on
MPS (0.192 at position 1), which checks the two platforms against each other. Accuracy plateaus after epoch
6, as the cosine schedule decays the learning rate, and train accuracy is only $\sim$2 points above
held-out, so the draft is not overfitting.

\paragraph{What the numbers say.} (i) Acceptance collapses after the first guess ($\alpha_2=0.06$). A chain
stops at the first miss, and guesses 2--3 are built on the draft's own hidden states. This is why
teacher-forced accuracy (0.31 / 0.27 / 0.25) overstates live acceptance. (ii) Serving is still
\emph{slower} than the target alone: one round costs $\sim$41\,ms, about 2.3 target-only steps of 18\,ms, but
yields only 1.32 tokens, so breaking even needs $\taubar\approx1.3$. (iii) Every gain must therefore come from
higher acceptance, which is what online training (BP-06) and the GRPO objective target, together with a
cheaper round (a draft KV cache). Positions 2--3 are exactly where an acceptance-based reward differs most
from forward KL, which weights all positions equally.

\section{Issues Faced}

\paragraph{Solved.}
\begin{itemize}
  \item \textbf{Compute and CUDA-only stack.} Full Aurora is out of reach, so we scaled down to Qwen3-0.6B on
  MPS and replaced SGLang, Mooncake, Ray and FSDP2 (Table~\ref{tab:mapping}), while reusing Aurora's
  algorithmic code unchanged.
  \item \textbf{No public draft and private data.} We trained our own EAGLE-3 draft (BP-04) on public
  datasets. In ShareGPT, 939 sampled threads started mid-conversation and 613 exceeded 1024 tokens; filters
  remove both.
  \item \textbf{Draft-vocab coverage.} A 16K draft vocab covered only 97.6\% of assistant tokens, and tokens
  outside it can never be drafted. 24K raises coverage to 0.993 / 0.995 / 0.998 (chat / code / math) for 8.2M
  more parameters and $\sim$1\,GB more peak memory, recovered by gradient checkpointing.
  \item \textbf{Memory on real sequences.} 4$\times$1K-token batches needed 9.9\,GB, beyond the 6--8\,GB
  estimate, because of the draft logits across three TTT steps. We use batch 2 with gradient accumulation
  and gradient checkpointing (2.4\,GB in training).
  \item \textbf{bf16 training underperforms.} With pure-bf16 AdamW at learning rate $10^{-4}$, small updates
  round away (all held-out accuracies 2--3 points lower). Aurora avoids this with fp32 master weights under
  FSDP, so we train in fp32. A reload bug that silently cast fp32 checkpoints to bf16 was found and fixed.
  \item \textbf{Exactness in bf16.} Scoring four tokens in one pass rounds slightly differently from four
  single-token passes, which can flip near-tied argmaxes. Losslessness checks therefore run in fp32, where
  they pass 150/150.
  \item \textbf{Under-trained baseline.} The first 2-epoch draft gave $\taubar=0.18$. Eight epochs raised it
  to 0.31 for 20 minutes of training.
\end{itemize}

\paragraph{Open.}
\begin{itemize}
  \item \textbf{No wall-clock speed-up yet} ($0.59\times$), as analysed above. Mitigations: online training,
  a draft-side KV cache, and reporting the estimated speed-up next to the measured one, since MPS overheads
  differ from a production GPU server.
  \item \textbf{Train/test overlap in the streams.} The 600 chat requests of the domain-shift stream, and
  900 of the 1000 chat requests in the mixed stream, were BP-04 training prompts. Before E2/E3 we must either
  rebuild the chat segments from held-out conversations or report results on the unseen segments only.
  \item \textbf{Single-device asynchrony.} Serving and training share one GPU, so ``async'' mode on the
  laptop competes for the same compute. Staleness will be real but smaller than in Aurora's two-server
  layout; E4 quantifies this.
  \item \textbf{GRPO prerequisites.} Groups of rollouts need tree drafting (top-$k>1$), which is not yet
  implemented (chain drafting only), and the reduced $K=3$ shortens the reward range compared with the paper's
  $K=5$.
  \item \textbf{Sharing artifacts.} Checkpoints (170\,MB) are not in git. We will publish the static draft
  as a GitHub release so all members start BP-06 from the same weights.
\end{itemize}

\section{Next Steps}

\begin{enumerate}
  \item \textbf{BP-06, online loop:} a bounded sample pool fed by the server, the BP-03 trainer, and weight
  publication every $N$ requests, in sync and async modes, from both day-0 and with-draft starts. Done when
  $\taubar$ rises over a 300-request day-0 run.
  \item \textbf{BP-07, metrics:} rolling $\taubar$, $\alpha_i$, speed-up, staleness histograms and loss curves

  \item \textbf{GRPO extension:} tree drafting for groups, reward $R(a)=L(a)-\lambda\kappa(K-L(a))$ computed

\end{enumerate}
