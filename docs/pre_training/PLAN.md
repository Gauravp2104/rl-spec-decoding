# Draft Pre-training Plan — Self-distilled Data for a Qwen3-1.7B Draft

Status: final (2026-10-30), replaces the 2026-10-28 plan (0.6B data-recipe arms, target × draft-depth grid).
Integration branch `pre-training` (off `base-paper`); sub-task branches `pt/NN-<slug>` → `pre-training`, issues and
PRs titled `[PT-NN] …`, label `pre-training`, GitHub Project "Draft pre-training". Scope: the **offline** EAGLE-3
draft that BP-04 produces and BP-06 / BP-08 start from. The online loop, the loss and the GRPO project are out of
scope.

## 1. Motivation

Every BP-08 arm starts from a weak offline draft. More ShareGPT data helps but slowly:

| draft | target | train data | held-out acc (pos 1 / 2 / 3) | τ̄ (held-out chat, K = 3) |
|---|---|---|---|---|
| `bp04-static-v1` | 0.6B | 900 chat, 8 ep | 0.311 / 0.271 / 0.248 | 0.315 |
| BP-09 | 1.7B | 900 chat, 8 ep | 0.354 / 0.292 / 0.260 | 0.319 |
| `kaggle_9k` | 0.6B | 9,000 chat, 8 ep | 0.516 / 0.451 / 0.417 | 0.623 |
| `kaggle_15k_6ep` | 0.6B | 15,000 chat, 6 ep | 0.539 / – / – | 0.671 |

The draft's labels already come from the target: the loss is a KL against the target's next-token distribution at
every position (`dump.py` stores the target's hidden states, and its `lm_head` gives the labels). What the
ShareGPT data fixes is the **context** those predictions are made in, which is text that ChatGPT wrote. At serving
time the context is Qwen3's own greedy output. On text it didn't write, the target is less confident and its
distributions are flatter. On its own text they are sharp, and that is what the draft has to match at serving
time. This plan trains on contexts the target wrote itself, first against BP-09 at 900 conversations, then at
~27K conversations.

**Expected effect: positive but modest.** EAGLE (Li et al., 2024) reports low sensitivity to fixed vs
target-generated training data, with a small gain from the latter. The mismatch may be larger here: Qwen3-1.7B with
thinking off writes shorter answers in a different style than ChatGPT. PT-01 checks for that gain cheaply before
PT-02 spends the large budget.

## 2. Research questions and design

**RQ1 (PT-01).** Starting from BP-09, does a Qwen3-1.7B draft trained on the **target's own answers** reach a
higher acceptance length than BP-09, which was trained on the **original ShareGPT answers** of the same 900
conversations?

**RQ2 (PT-02).** Does training on target outputs keep helping when scaled from 900 to ~27K conversations?

| arm | work item | target | prompts | assistant turns | epochs |
|---|---|---|---|---|---|
| **A0** (ground-truth baseline) | PT-01 | Qwen3-1.7B | BP-09's 900 chat | ShareGPT original | 8 — the existing BP-09 checkpoint, re-evaluated |
| **A1** (self-distilled) | PT-01 | Qwen3-1.7B | same 900 | **regenerated by Qwen3-1.7B, greedy** | 8 |
| **B1** (self-distilled, scaled) | PT-02, only if PT-01 passes | Qwen3-1.7B | all filtered ShareGPT chat outside the BP-02 pool (~26.5K) | **regenerated by Qwen3-1.7B, greedy** | 4 |

In PT-01 only the assistant turns differ between A0 and A1. The user turns, the conversation IDs, the held-out split
and every training setting are the same, so A1 − A0 is the self-distillation effect.

**Hypothesis (stated before measuring).** A1 > A0 on held-out chat τ̄. The gain should be largest at positions 2–3
(α2, α3), where the draft conditions on its own earlier guesses and a distribution mismatch compounds. B1 should
then land well above A1, the 900 → 27K data-scale effect.

## 3. Fixed controls

| setting | value |
|---|---|
| target | Qwen3-1.7B, 28 layers, hidden 2048 |
| draft | 1 decoder layer, hidden 2048, 16 heads / 8 KV (head_dim 128), intermediate 6144: the BP-09 config, ~120M trainable params with the 24K `lm_head` |
| aux layers | EAGLE-3 rule `[1, L/2 − 1, L − 4]` → 1 / 13 / 24 |
| draft vocab | 24K mixed (`outputs/vocab/qwen3_24k_mixed.pt`) |
| draft init | embedding copied from the target and frozen; everything else random (as BP-04) |
| TTT length / K | 3 / 3 |
| loss | Σ 0.8ⁱ · forward-KL_i against the target's pruned distribution |
| optimizer | AdamW, LR 1e-4, warmup 1.5% + cosine over the run, grad clip 0.5, batch 2 × accumulation 4 |
| epochs | 8 in PT-01 (matches BP-09); 4 in PT-02 to bound cost (27K × 4 ≈ 106K conversation-epochs, more than `kaggle_15k_6ep`'s 90K) |
| precision | fp32 draft weights + gradient checkpointing; fp32 target for generation, dumps and τ̄ |
| sequence | ≤ 1024 tokens per training sequence |
| chat template | `enable_thinking=False`, identical in generation, dump and serving |
| serving | greedy, bs = 1, 128 new tokens, KV-cached target, `--check` on |

## 4. Self-distilled data (A1, B1)

For each training conversation, keep the user turns and regenerate every assistant turn **sequentially** with
Qwen3-1.7B: turn i is generated given the user turns and the target's own earlier answers.
- greedy decoding in fp32, `enable_thinking=False`, ≤ 512 new tokens per turn;
- batched across conversations at the same turn index (left padding), resumable shards;
- truncate to 1024 tokens;
- loss mask on the regenerated assistant tokens, including the end-of-turn token;
- drop exact-duplicate responses but keep repetitive ones, because greedy serving produces them too;
- log the share of turns that hit the 512 cap or loop, and the assistant-token count per arm.

The same script (`mini_aurora/data/regenerate.py`, written in PT-01) produces B1's data in PT-02. Conversations
already regenerated in PT-01 are reused.

## 5. Evaluation

**Held-out set.** `chat-00900` … `chat-00999`, the BP-04 held-out split, which is excluded from all training data.
It keeps τ̄ comparable with every row of §1. Also report 100 CodeAlpaca and 100 GSM8K stream rows as out-of-domain
checks; no arm trains on code or math.

**Per arm (A0 re-evaluated with the same harness):**
- τ̄ with a 95% bootstrap CI over requests, and α1 / α2 / α3;
- lossless count, which must be 100/100 (chat) or the run is invalid;
- teacher-forced top-1 accuracy per position on the held-out dumps;
- tok/s and measured speed-up S against target-only decoding on the same device and dtype.

**Optional, serve-only (PT-02).** Tree drafting (`serve.py -k 3 --tree-topk {2,4} --tree-beam {2,4}`) on A0, A1 and
B1. It needs no retraining and shows whether the self-distillation gain carries over to trees.

## 7. Compute and disk budget

These are estimates scaled from the 0.6B 9K run (dump 58 min, train 6.1 h on a T4) and BP-09. Measured numbers
replace them.

| step | where | GPU time | disk, peak |
|---|---|---|---|
| PT-01 regeneration (900) | T4 or A100 | < 0.5 h | negligible |
| PT-01 dump + train A1 | T4 | ~2 h | ~8 GB dump |
| PT-01 eval, A0 + A1 | T4 or Mac | ~1 h | – |
| PT-02 regeneration (~26.5K) | Zaratan A100 | ~5 h (batched; bs = 1 would take ~100 h) | < 1 GB of text |
| PT-02 dump | Zaratan A100 | ~3 h | **~240 GB** (4 × 2048 × 2 bytes ≈ 16 KB per token) |
| PT-02 train (4 ep) | Zaratan A100 | ~6 h | ~1.5 GB checkpoints |
| PT-02 eval | Zaratan A100 | ~1 h | – |
| **PT-02 total** | | **~15 A100-h ≈ 720 SU** at 48 SU/h | |

- The dump is deleted once B1 has trained.
- 240 GB likely exceeds the free space on the shared course scratch. Check `df -h ~/scratch.msai635` first. If it
  doesn't fit, dump and train in chunks (e.g. 4 × ~6.6K conversations per epoch pass), or compute the target's
  hidden states inside the training step instead of dumping them.
- The 1.7B target in fp32 is ~7 GB of weights, so it also fits a MIG slice for evaluation. Generation, dumps and
  training run on full A100s.

## 8. Decision rules

- **PT-01 → PT-02.** Go if A1's held-out chat τ̄ beats A0's by more than 0.02. Report both 95% bootstrap CIs; if they
  overlap, rerun A1 with a second seed before committing the PT-02 budget. Otherwise stop and reconsider.
- Any configuration with fewer than 100/100 lossless outputs is excluded and debugged.
- If PT-02 runs, B1 becomes the new offline draft for 1.7B-target experiments.

## 9. Risks

- **Single seed.** One training seed per arm, so seed variance isn't measured. The bootstrap CI covers request
  variance only. If A1 − A0 is near the 0.02 threshold, rerun A1 with a second seed.
- **No ground-truth arm at 27K.** PT-02 trains only the self-distilled arm, so B1's gain over A1 mixes data scale
  with self-distillation. The 0.6B `kaggle_9k` / `kaggle_15k_6ep` rows give context only. A 27K ground-truth arm
  (~10 A100-h more) is the fix if budget allows.
- **Greedy loops.** Greedy regeneration can produce repetitive answers. If more than ~10% of turns loop or hit the
  cap, add a sampled-regeneration arm (T = 0.7).
- **Disk and queue.** The full-A100 queue for this account has waited hours, and the dump may not fit on scratch.
  Fallback: run PT-02 on the first 9K conversations.
- **Comparability with 0.6B results.** No 0.6B arm is run, so BP-04 / BP-08 numbers are context only.
