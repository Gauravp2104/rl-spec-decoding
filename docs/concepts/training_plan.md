# Training plan: B1 → GRPO

**In one line:** train one strong self-distilled 1.7B draft (B1), release it, then start three arms from it on the
same request stream (static, Aurora's online forward-KL, our online GRPO) and compare acceptance τ̄ and real speedup
over the target alone. Background: [speculative_decoding.md](speculative_decoding.md). History of how we got here:
[`../base_paper/PLAN.md`](../base_paper/PLAN.md) (Phase 1) and [`../pre_training/PLAN.md`](../pre_training/PLAN.md)
(PT-00 … PT-03).

## 1. B1: the starting checkpoint (PT-02, Zaratan)

Qwen3-1.7B target, ~26.5K ShareGPT chat conversations with every assistant turn regenerated by the target (greedy),
4 epochs of the BP-09 / A1 recipe. Job chain and options: [`mini_aurora/zaratan/README.md`](../../mini_aurora/zaratan/README.md).

| step | does | cost |
|---|---|---|
| `pt02_prepare.sh` (login) | 26.5K pool + 100 held-out rows, 8 parts, A1 checkpoint, disk check | ~20 min |
| `SMOKE=1 submit_pt02.sh` | whole chain at tiny scale | ~1 A100-h |
| regen (array of 8) | Qwen3-1.7B rewrites every assistant turn | ~5–10 A100-h |
| dump → train | target features (~240 GB, sharded) → 4 epochs | ~10–14 A100-h |
| eval b1, a1 | K = 3 chain on chat / code / math, **K = 6 / top-k 3 / beam 8 tree** on held-out chat | ~2–3 A100-h each |
| `pt02_release.sh stage` → `publish` | checks, notes, SHA256SUMS → draft release `pt02-b1-v1` | – |

About 800–1,150 SU and ~2 days including the queue. **B1's K = 6 tree τ̄ is the bar GRPO must beat.**

```bash
bash mini_aurora/zaratan/pt02_prepare.sh
SMOKE=1 bash mini_aurora/zaratan/submit_pt02.sh
TREES=1 bash mini_aurora/zaratan/submit_pt02.sh
bash mini_aurora/zaratan/pt02_release.sh stage && bash mini_aurora/zaratan/pt02_release.sh publish
```

## 2. GRPO: what to build

Develop on A1 (release `pt01-a1-v1`, same architecture and vocab as B1) while PT-02 runs; switch to B1 when released.

1. **Sampled trees.** The draft samples its top-k children with a temperature instead of the argmax, and records the
   behaviour log-prob of each path. The target still verifies greedily, so output stays lossless.
2. **Reward.** Each path's accepted length, read off the same verify pass. A round with beam 8 gives a **group of
   ~8 paths** at no extra target cost.
3. **Advantage.** A_i = (r_i − mean(r)) / std(r) within the round's group.
4. **Loss.** Clipped off-policy GRPO ratio π_θ(path) / π_behaviour(path) × A_i, plus the forward-KL distillation loss
   as an anchor (weight β) so the draft does not drift from the target's distribution.
5. **Online loop.** Reuse BP-06: the server streams requests and logs paths, log-probs, rewards and draft versions;
   the trainer updates and hot-swaps the draft; samples more than Δ versions stale are dropped.

## 3. Experiment

All arms start from B1, run the same stream, and draft with the K = 6 / top-k 3 / beam 8 tree.

| arm | draft updates |
|---|---|
| A: static | none (B1 as released) |
| B: online forward-KL | Aurora's loss (Phase 1 reproduction) |
| C: online GRPO | ours |

- **Metrics:** rolling τ̄ and α_i over the stream, lossless 100%, **speedup = speculative tok/s ÷ target-only tok/s**
  (`--check` logs both).
- **Success:** C reaches a higher τ̄ than B at equal training steps, and C's speedup over target-only is above 1×.
- **Measurement:** speed on an A100 in bf16 with the KV cache, reporting τ̄ next to time per round; fp32 T4 trees cost
  more per round than they gained in τ̄.
